# 智绘生物

## 1. 项目定位

智绘生物是一个面向真实课堂场景的多模态 AI 教学系统。它不是单点的 PPT 生成工具，而是把教师从备课到课堂执行再到导出交付的完整工作流做成了一条可运行、可部署、可迭代的智能链路。

系统围绕三个真实问题设计：

1. 教师备课链路割裂，需要在资料整理、课件制作、教案撰写、互动设计之间频繁切换。
2. 通用大模型生成结果容易空泛，难以稳定贴合学科目标、教材内容和课堂节奏。
3. 很多“AI 教学”产品只停留在内容生成，没有真正进入课堂执行层，无法支撑互动、讲解和资源交付。

因此，本项目的核心目标不是“生成一份内容”，而是“生成一节能上、能讲、能互动、能导出的课”。

## 2. 面向用户期望的系统价值

项目的设计不是从模型能力出发，而是从教师的真实期望倒推：

| 用户真实期望 | 系统响应能力 | 直接价值 |
|---|---|---|
| 输入越少越好，但首版结果必须能用 | 多轮对话采集需求，自动抽取教学意图 | 降低描述成本，提高首轮命中率 |
| 结果不能空话套话，要贴教材和课堂目标 | 参考资料解析 + RAG 检索增强 + 结构化生成 | 输出更可信，更贴近真实教学 |
| 不只要 PPT，还要能支撑上课 | 教案、互动游戏、课堂讨论、数字人讲解联动生成 | 从“生成内容”升级为“生成课堂流程” |
| 生成后必须能继续打磨 | 支持多轮迭代优化、历史版本延展 | 教师可持续修改，不必推倒重来 |
| 要能本地部署，不依赖复杂在线平台 | 前端、主后端、数字人服务解耦 | 方便竞赛演示、学校内网和本地交付 |

## 3. 项目整体亮点

### 3.1 全流程闭环，而不是碎片化工具

项目覆盖了：

1. 教学需求采集
2. 教学意图结构化理解
3. 参考资料解析与知识增强
4. 课件与教案生成
5. 互动内容生成
6. 数字人课堂讲解
7. 资源导出与本地部署

这意味着教师不需要在“聊天工具、PPT 工具、文档工具、互动平台、语音工具”之间来回跳转。

### 3.2 多模态资料进入同一条生成链路

系统不是只接收纯文本需求。教师上传的图片、文档、音频、视频资料会被解析、清洗、整理为统一的上下文，再共同约束生成结果。相比只看一段 prompt 的普通生成方式，这种设计更能还原真实备课过程。

### 3.3 课堂可执行，不是静态展示

项目重点不是把页面做得“像 AI 产品”，而是让内容真正能在课堂中跑起来：

1. 互动游戏具备可执行 HTML 结构
2. 数字人具备会话加载、页面讲解、语音播报能力
3. 白板与互动组件能进入课堂流程而不是停留在展示层

### 3.4 工程上可落地

系统并没有把所有逻辑塞进一个巨型服务，而是采用了前端、主后端、数字人服务分层。这样做的价值很直接：

1. 问题隔离更清晰
2. 服务可以独立调试和替换
3. 部署路径更符合实际工程要求

## 4. 核心创新点

### 4.1 创新点一：意图优先，而不是模板优先

很多教学生成系统的本质仍然是“模板填空”，用户一旦描述不充分，生成质量就迅速下降。智绘生物先做的是教学意图建模，再做内容生成。

项目中对教学意图的理解不是一句模糊总结，而是结构化抽取多个关键维度，包括：

1. 学科与年级
2. 章节与知识点
3. 教学目标与重难点
4. 教学逻辑与内容组织方式
5. 活动建议与互动偏好
6. 输出物需求

这使系统理解的是“这节课应该怎样组织”，而不只是“这节课主题是什么”。

### 4.2 创新点二：三源融合生成，而不是单轮 Prompt 输出

项目中的生成结果并不是单纯由用户输入决定，而是由三类来源共同约束：

1. 教师通过多轮对话表达的教学意图
2. 用户上传的教材、图片、讲义、参考资料
3. 本地知识库 RAG 检索出的相关上下文

这套机制的创新价值在于，它把大模型从“自由发挥”收束为“在教学目标、教师资料和检索证据三重边界内生成”，显著降低了偏题、失真和幻觉。

### 4.3 创新点三：生成的不只是课件，而是整节课的执行结构

系统输出的不只是 PPT 页面内容，还包括：

1. 教案文本
2. 课堂互动游戏
3. 教学讨论素材
4. 数字人讲解文案与播报任务
5. 可导出的教学资源包

这意味着系统完成的是从“内容生产”向“课堂执行编排”的升级。

### 4.4 创新点四：互动内容与本次课堂强相关

项目强调互动内容必须与本次课堂生成内容相关，而不是无关的通用题库或随机小游戏。互动游戏模板负责交互结构，生成引擎负责注入本节课的知识点、概念关系、判断逻辑和教学目标，因此互动部分不是装饰，而是教学过程的一部分。

### 4.5 创新点五：数字人形象驱动声线，而不是固定默认语音

数字人不是只有一个静态声音。系统尝试利用多模态模型对头像形象进行解析，抽取年龄感、能量感、温暖度、气质描述和语速建议，再映射到可用的语音能力上，从而形成更接近人物形象的声音呈现。这比传统 TTS 里手动选一个 voice 的方式更接近真正的角色化教学表达。

### 4.6 创新点六：服务解耦带来的可扩展创新

项目把“教学内容生成”和“数字人播报”拆成独立服务，这不仅是工程实现手段，也是架构创新点。它允许：

1. 教学链路继续扩展更多生成能力
2. 数字人链路独立切换语音模型或多模态服务
3. 在竞赛演示、本地测试、校内部署中按需裁剪能力

## 5. 技术架构

### 5.1 服务拓扑

项目分为三层：

1. `frontend`：Next.js 前端，负责交互、状态管理、UI 渲染和 API 代理
2. `backend`：FastAPI 主后端，负责教学意图理解、RAG、课件/教案/互动内容生成
3. `digital-human`：FastAPI 数字人后端，负责数字人会话、播报任务、音频缓存与语音输出

默认端口：

- 前端：`3000`
- 主后端：`9527`
- 数字人服务：`8000`

### 5.2 为什么要分成三层

这样拆分不是为了“看起来高级”，而是为了解决真实问题：

1. 前端只关心课堂交互与展示逻辑，不直接承担复杂生成编排
2. 主后端专注教学内容生成，可独立调试 RAG 和模型路由
3. 数字人服务可以单独替换 TTS、语音模型或形象分析能力

最终结果是：问题定位更容易，扩展成本更低，部署更加清晰。

## 6. 扎实的技术细节

### 6.1 多轮对话与状态机驱动的需求采集

系统并不是把用户第一句输入直接丢给生成模型，而是通过多轮对话逐步补齐关键信息。后端对话管理采用显式状态推进，覆盖问候、信息收集、确认、准备生成、生成中、迭代优化等阶段。这种设计的价值在于：

1. 能识别当前信息是否完整
2. 能明确缺少哪些关键字段
3. 能在生成前进行确认，减少误生成
4. 能在生成后继续进入迭代优化阶段

这套链路对应的实现位于：

- [dialogue_manager.py](/d:/ITO/ITO/backend/src/rag/dialogue/dialogue_manager.py)

### 6.2 结构化教学意图抽取

教学意图抽取不是松散的自然语言总结，而是固定结构的数据对象。当前意图结构至少覆盖：

1. 学科
2. 年级
3. 章节
4. 知识点
5. 教学逻辑
6. 重点
7. 难点
8. 建议活动
9. 内容板块
10. 游戏建议

这种结构化设计使后续生成链路可以稳定依赖这些字段，而不是每次重新猜测用户真实意图。

对应实现位于：

- [intent_extractor.py](/d:/ITO/ITO/backend/src/rag/dialogue/intent_extractor.py)

### 6.3 RAG 不只是“查一下资料”，而是带证据和 trace 的生成辅助

项目中的 RAG 服务不仅返回答案，还会统一组织：

1. 检索证据列表
2. 来源定位信息
3. trace 日志
4. 面向用户展示的 `human_view`

这意味着系统不仅能“给答案”，还能说明“这个答案来自哪里、检索到了什么、处理链路做了什么”。这对于教学场景尤其重要，因为教师更关注结果的可追溯性，而不是只看一句最终文本。

对应实现位于：

- [service.py](/d:/ITO/ITO/backend/src/rag/service.py)

### 6.4 统一模型路由，而不是散落式 API 调用

主后端对大模型调用采用了统一路由层，核心能力包括：

1. 按任务类型选择模型
2. 请求重试与指数退避
3. JSON 提取与 schema 校验
4. 内容哈希缓存
5. 错误类型归一化
6. 流式生成支持

这个设计非常关键。因为系统不是只做一种任务，而是同时做意图理解、课件内容生成、互动内容生成、多模态分析等多种任务。如果模型调用散落在代码里，后期几乎无法调优和维护。统一路由意味着整个系统具备“模型治理能力”，这是一个成熟工程的重要标志。

对应实现位于：

- [router.py](/d:/ITO/ITO/backend/src/rag/infrastructure/llm/router.py)

### 6.5 多模态资料解析进入统一知识上下文

项目支持将 OCR、ASR、图像理解等多模态解析结果汇入同一条生成链路。这样做的关键意义在于：

1. 图片不再只是附件，而能成为教学上下文的一部分
2. 音视频资料可以被转写并参与知识融合
3. 多种来源最终都能以统一方式服务于生成和互动

这是项目从“文本型工具”进化为“多模态教学系统”的基础能力。

### 6.6 互动游戏不是静态页面，而是可执行前端运行时

项目中的课堂游戏模板不是几段普通 JSON，而是实际可执行的 HTML/CSS/JS 模板运行时。模板内集成了动画、排序、匹配、判断、填空、翻卡等交互组件能力，并允许把当前课堂语义内容注入模板结构。

当前模板能力覆盖：

1. 选择判断类
2. 连线匹配类
3. 排序推理类
4. 填空类
5. 对错判断类
6. 翻卡记忆类
7. 流程填充类

这意味着互动不只是“样式像游戏”，而是真的具备用户输入、提交、反馈、动画和状态变化。

对应实现位于：

- [game_templates.py](/d:/ITO/ITO/backend/src/rag/game/game_templates.py)

### 6.7 数字人服务是完整链路，不是简单按钮调用

数字人服务包含完整的后端职责：

1. 健康检查
2. 课堂会话加载
3. 播报任务创建
4. 文本到音频合成
5. 音频缓存
6. 持久化元数据记录
7. 前端可访问的音频 URL 输出

这使数字人真正具备课堂使用能力，而不是“点击后随机播一下语音”。

### 6.8 数字人声线匹配的多模态实现细节

项目中为数字人做了一个重要增强：先解析头像，再决定声音。具体链路是：

1. 读取头像引用、来源和人物提示信息
2. 使用多模态模型输出声音画像 JSON
3. 提取声线、语速、风格短句等字段
4. 将这些信号映射为最终可调用的 TTS 参数
5. 把生成后的声线画像缓存到会话元数据中

相比传统“固定 voice + 固定 speed”的方案，这种链路更接近真正的角色一致性建模。

对应实现位于：

- [voice_profile.py](/d:/ITO/ITO/digital-human/avatar_service/services/voice_profile.py)

### 6.9 数字人 TTS 的缓存与运行时配置能力

数字人音频合成服务不是简单地把文本送去生成。它还做了：

1. 速度归一化
2. 缓存 key 构建
3. 音频文件与元数据分离存储
4. 时长估计与格式统一
5. 运行时 provider/model/base URL 注入

这意味着数字人语音链路具备较好的性能复用能力和后续扩展空间。

对应实现位于：

- [tts.py](/d:/ITO/ITO/digital-human/avatar_service/services/tts.py)

## 11. 前端用户功能与按钮服务详解

这一部分不再讲部署，而是专门说明用户在前端真正会看到、会点击、会使用的功能，以及这些按钮背后实际触发了什么前端逻辑、状态管理和后端服务。

本项目的前端不是“静态展示壳子”，而是一个课堂工作台。用户点击的每一个按钮，基本都对应明确的状态切换、数据持久化、服务代理或生成链路。

### 11.1 首页生成区：从需求输入到课程生成

首页不是简单的输入框页面，而是“生成任务配置台”。它把模型、资料、输出形式和生成偏好都集中在一个地方，让用户先把任务条件讲清楚，再进入课程生成。

#### 11.1.1 生成区主要按钮与作用

| 用户看到的入口 | 用户动作 | 前端层发生的事 | 服务或状态链路 | 最终结果 |
|---|---|---|---|---|
| 模型选择器 | 选择语言模型和具体模型 | 从设置仓库读取当前 provider/model，切换当前生成模型 | `useSettingsStore` 保存模型配置 | 后续大纲生成、场景生成、互动生成都会使用当前模型 |
| 语言切换 | 切换中英文界面 | 修改国际化 locale | `useI18n()` + 本地状态 | 整个界面文案、按钮文本、部分生成偏好切换 |
| PDF 按钮 | 上传 PDF 教材/资料 | 校验格式和大小，绑定 PDF 解析 provider | `GenerationToolbar` + PDF provider 配置 | PDF 进入资料解析链路 |
| 参考资料上传 | 上传 Word、PPT、图片、视频、音频、文本等 | 做大小过滤、去重、缓存文件列表 | `referenceFiles` + `referencePurposes` | 多模态资料进入课程生成上下文 |
| 参考用途标注 | 给每个文件标记“知识点/案例/习题/排版风格”等用途 | 前端为每个文件建立用途标签 | 目的标签随生成参数一起传递 | 后端更清楚该文件该如何被利用 |
| 图片素材库 | 选择参考图片 | 打开素材弹层，将图片纳入输入上下文 | `ImageLibraryDialog` | 支持“用图指导生成” |
| 输出预设 | 选择“极速备课 / 教学增强 / 创新互动” | 批量改写输出类型集合 | `outputTypes` | 决定最终是只出 PPT+教案，还是同时出动画/互动页 |
| 输出类型按钮 | 单独勾选 PPT、教案、互动游戏、概念动画 | 切换输出工件集合 | `OutputArtifactType[]` | 控制具体产出形态 |
| Web 搜索开关 | 开关联网补充能力 | 校验 Web Search provider 是否可用 | Web Search provider config | 允许生成时补充外部知识 |
| 设置按钮 | 打开设置页 | 打开 provider、ASR、TTS、数字人、知识库等设置 | `SettingsDialog` | 管理整个系统的模型、音频和数字人能力 |

#### 11.1.2 首页配置为什么重要

这些按钮不是“辅助 UI”，而是生成质量控制系统的一部分：

1. 模型选择决定意图理解、场景生成和互动页生成的基础能力。
2. 参考资料决定内容是否真正贴近教师想讲的内容。
3. 输出类型决定系统最后输出的是“内容片段”还是“整节课的多工件组合”。
4. Web 搜索和知识库配置决定系统是纯本地生成还是检索增强生成。

换句话说，首页生成区承担的是“任务声明”和“生成约束配置”，不是普通输入框。

### 11.2 课堂页：不是单页展示，而是完整教学工作台

进入课堂页后，整个界面被拆成几个强职责区：

1. 左侧场景目录：管理课件页、测验页、互动页、PBL 页。
2. 中间主舞台：展示当前页内容，是课堂主视图。
3. 下方/前景控制层：负责播放、暂停、讨论、白板、音量、自动播放等课堂操作。
4. 右侧笔记与聊天区：展示讲稿笔记、课堂讨论记录和多角色对话。
5. 悬浮数字人区：负责数字人讲解、打招呼、本页说明和问答。
6. 白板浮层：提供即时书写、擦除、回滚与历史恢复。

课堂页本身还承担持久化与恢复职责：

1. 先从本地 IndexedDB 恢复课堂数据。
2. 如果本地没有，再向 `/api/classroom` 拉取服务器侧课堂快照。
3. 场景生成未完成时自动续跑剩余 outline。
4. 媒体任务和已生成角色会自动恢复。
5. 白板修改会同步回课堂快照，避免刷新后丢失。

这意味着课堂页不是“查看页面”，而是“运行时页面”。

### 11.3 左侧场景目录：课堂结构控制器

左侧场景目录对应整节课的结构导航。它不仅显示页列表，还把每一页的类型、缩略图和当前状态暴露给用户。

#### 11.3.1 用户能做什么

1. 点击任意场景卡片，快速跳转到该页。
2. 通过缩略图预览不同页内容。
3. 识别不同页类型：普通讲解页、测验页、互动页、PBL 页。
4. 在生成失败时触发重试 outline。
5. 拖拽调整侧边栏宽度。
6. 一键折叠侧边栏，把空间让给主舞台。

#### 11.3.2 技术上怎么实现

1. 场景目录读取 `useStageStore()` 中的 `scenes`、`currentSceneId`、`generationStatus`、`failedOutlines`。
2. 缩略图不是固定图片，而是从场景内容动态渲染。
3. 普通 slide 使用真实缩略渲染；quiz / interactive / pbl 使用对应样式化缩略结构。
4. 点击场景时调用 `setCurrentSceneId()` 切换当前课堂页面。

它的作用相当于“课程流程导航器”。

### 11.4 课堂主控条：课堂播放、讨论、白板、音量都在这里

课堂底部/中部的主控条是最关键的用户操作区之一。这里几乎集中了课堂执行层的所有高频按钮。

#### 11.4.1 主控条按钮与服务映射

| 按钮 | 用户效果 | 前端行为 | 服务/引擎链路 | 持久化/结果 |
|---|---|---|---|---|
| 左侧目录开关 | 折叠/展开课程目录 | 修改侧边栏显示状态 | `useSettingsStore.sidebarCollapsed` | 课堂视图布局改变 |
| 页码指示 | 显示当前页 / 总页数 | 纯展示型状态 | 当前 `scene` 状态 | 用户知道当前教学进度 |
| 音量静音按钮 | 一键静音/取消静音 | 切换 TTS muted 状态 | `audioPlayer` + `useSettingsStore.ttsMuted` | 课堂播报即时静音 |
| 音量滑杆 | 调节课堂播放音量 | 实时修改音量 | `audioPlayer.setVolume()` | 当前讲课音频实时变大/变小 |
| 播放速度 | 循环切换 1x / 1.25x / 1.5x 等 | 改写播放速度状态 | `PlaybackEngine` + `audioPlayer` | 讲解节奏改变 |
| 上一页 / 下一页 | 页面切换 | 切换当前 scene | `setCurrentSceneId()` | 用户手动控制讲课顺序 |
| 播放 / 暂停 | 启动或暂停课堂播放 | 控制引擎状态 | `PlaybackEngine` + `ActionEngine` | 课堂讲解开始或暂停 |
| 停止讨论 | 强制结束当前讨论/问答 | 终止当前活跃聊天会话 | `ChatArea.endActiveSession()` + `Stage.doSessionCleanup()` | 中断 SSE、多角色停讲、界面回到稳定态 |
| 自动播放 | 自动推进下一页 | 切换自动播放状态 | `useSettingsStore.autoPlayLecture` + `PlaybackEngine.onComplete` | 讲完自动进下一页 |
| 白板按钮 | 打开/收起白板 | 切换白板显示状态 | `useCanvasStore.whiteboardOpen` | 白板浮层显示或隐藏 |
| 聊天按钮 | 打开/收起右侧聊天区 | 切换聊天区布局 | `useSettingsStore.chatAreaCollapsed` | 课堂右侧区域收起或展开 |

#### 11.4.2 为什么这个主控条重要

它把“播放控制、音频控制、课堂交互控制、布局控制”压缩到一条统一工具带里，使课堂不需要跳转页面或弹出复杂面板，就能完成讲课和互动。

### 11.5 白板：用户真能写、能擦、能清空、能恢复

白板不是一个装饰层，而是真正可交互、可保存、可恢复的课堂工具。

#### 11.5.1 白板中用户能看到和点击的按钮

| 白板按钮 | 用户行为 | 具体作用 |
|---|---|---|
| 画笔模式 | 进入书写模式 | 用鼠标或触控直接在白板上写字或画线 |
| 拖动画布模式 | 进入平移模式 | 对已有白板内容进行拖拽查看 |
| 橡皮擦模式 | 擦除笔迹 | 按笔画命中删除内容 |
| 线宽按钮 | 切换 2 / 3 / 5 px | 改变当前书写粗细 |
| 撤销上一笔 | 撤回最近一组线段 | 撤销最后一笔完整书写 |
| 清空白板 | 一键删除当前白板内容 | 删除所有元素，保留历史快照 |
| 历史按钮 | 打开历史面板 | 查看快照列表并恢复 |
| 恢复按钮 | 恢复某个快照 | 事务性替换白板全部元素 |
| 最小化 | 收起白板 | 退出浮层但保留内容 |
| 重置视图 | 在平移/缩放后回到默认视图 | 用于快速回正画布 |

#### 11.5.2 白板写入链路非常具体

当用户在白板上书写时，前端不是等很久后再保存，而是分两层处理：

1. 绘制中，先用临时 `polyline` 在前端即时显示笔迹，保证书写过程“当下就能看到”。
2. 抬笔时，把一整笔轨迹离散成多段 `line` 元素。
3. 这些 `line` 元素通过 `stageAPI.whiteboard.update()` 立即写回课堂状态。
4. `createWhiteboardAPI()` 内部用 `queueMicrotask()` 触发 `saveToStorage()`，把结果写入本地持久化。
5. 课堂页监听 `stage/scenes` 变化，使用 120ms 的轻量节流把快照 POST 到 `/api/classroom`。

所以白板的保存链路实际上是：

`用户画线 -> 临时前端渲染 -> 写入 stage store -> 本地存储 -> 服务器课堂快照同步`

这也是为什么白板不是“写完消失、稍后再保存”的弱交互，而是即时可见、即时入状态、很快同步。

#### 11.5.3 橡皮擦不是全删，而是命中删除

橡皮擦模式下：

1. 系统会把鼠标位置换算成白板内容坐标。
2. 对已有 `line` 元素做命中检测。
3. 命中后优先按 `groupId` 删除整笔，而不是只删零碎单段。

这样用户擦除时的体验更接近真实白板。

#### 11.5.4 清空和历史恢复不是互相冲突的

白板清空前会先保存快照：

1. 清空前把当前元素压入 `useWhiteboardHistoryStore`。
2. 触发级联退出动画。
3. 动画结束后真正执行删除。

白板历史恢复时：

1. 先阻止“清空动画尚未结束”的恢复操作，避免状态覆盖。
2. 用元素指纹避免“重复恢复同一状态”的无效操作。
3. 用一次性事务更新替换整个白板内容，而不是逐元素删增。

当前白板历史特性包括：

1. 最多保存 20 条快照。
2. 自动跳过重复快照。
3. 恢复后不会立即再把同一内容当作新快照重复记录。

### 11.6 右侧笔记区与聊天区：一边授课，一边留下课堂痕迹

右侧区域不是普通聊天面板，它有两个角色：

1. `Lecture` 标签页：记录讲稿、动作、讨论触发点。
2. `Chat` 标签页：记录问答会话和多角色课堂讨论。

#### 11.6.1 Lecture 标签页

Lecture 区会从当前场景动作中自动抽取：

1. `speech`
2. `spotlight`
3. `laser`
4. `play_video`
5. `discussion`

这意味着它不是额外生成一份“笔记”，而是把真实课堂动作结构化回放给用户，方便复盘和查阅。

#### 11.6.2 Chat 标签页

Chat 区负责显示：

1. 课堂讨论会话
2. 用户追问
3. 多角色回复
4. 当前活跃会话状态
5. 会话结束按钮

它还支持：

1. 面板拖拽调宽
2. 一键折叠
3. 当前有活跃讨论但你还停留在 Lecture 页时，Chat 标签会显示提醒点

### 11.7 文本输入、录音输入、发送按钮：课堂问答入口

课堂中用户和系统交互主要有两个入口：

1. 文本输入
2. 语音输入

这两个入口都挂在圆桌/课堂交互层，而不是单独跳转到聊天页。

#### 11.7.1 文本输入按钮

文本输入流程是：

1. 打开输入框。
2. 用户输入问题或指令。
3. 点击发送。
4. 前端先把用户消息显示出来。
5. 调用 `onMessageSend()` 进入当前对话/讨论会话。
6. 进入发送冷却状态，直到系统真正开始回复，避免重复点击造成重复发送。

这个“发送冷却”是专门做的稳定性保护，不是普通禁用按钮。

#### 11.7.2 录音按钮

录音按钮背后有两套逻辑：

1. 如果 ASR 设置为浏览器原生识别，优先使用 `SpeechRecognition / webkitSpeechRecognition`。
2. 如果使用服务端 ASR，则用 `MediaRecorder` 采集音频，上传到 `/api/transcription`。

`/api/transcription` 的后端代理做了这些事：

1. 识别音频格式
2. 解析 providerId、language、apiKey、baseUrl
3. 调用配置的 ASR provider
4. 如果主 provider 是 `qwen-asr` 且失败，自动回退到 `openai-whisper`

这使录音功能在服务不稳定时仍有一定容错能力。

#### 11.7.3 录音输入的用户体验保护

录音链路还做了几项细节处理：

1. 网络错误、超时、`fetch failed`、5xx 会自动重试最多 2 次。
2. 当浏览器或服务端都不可用时，会给出明确错误文案，而不是静默失败。
3. 语音转文本为空时，不会提交空消息进入课堂。
4. 当当前消息处于发送冷却阶段时，会阻止新一次录音提交，避免多次覆盖。

### 11.8 主动讨论卡片与多角色课堂讨论

课堂中的讨论不是“只有一个 AI 教师一直讲话”。系统支持多角色参与的课堂讨论机制，并且有明确的前端入口。

#### 11.8.1 主动讨论卡片

当课堂动作流触发讨论时，会在指定角色头像附近弹出主动讨论卡片。卡片包含：

1. 讨论主题
2. 发起角色
3. 倒计时
4. 参与按钮
5. 暂停/继续按钮
6. 跳过按钮

这张卡片不是浮动文案，而是课堂“讨论触发器”。

#### 11.8.2 用户点击后的服务链路

1. `PlaybackEngine` 在动作序列中触发 `DiscussionAction`。
2. Stage 把讨论请求交给 `ChatArea.startDiscussion()`。
3. 前端切换到 Chat 标签。
4. SSE 会话开始流式返回角色发言。
5. 圆桌区域同步显示谁在说话、谁在思考、当前是讨论还是问答。
6. 如果用户手动停止，会走 `endActiveSession()` + `doSessionCleanup()`，统一清理讨论状态。

这个讨论系统因此不是“随机冒一句话”，而是可中断、可恢复、可收尾的课堂会话系统。

### 11.9 数字人助教：连接、会话、打招呼、讲解本页、问答、声音开关

数字人区域是课堂中另一个非常具体的用户入口。它不是一个装饰头像，而是完整的前端小控件。

#### 11.9.1 用户能看到什么

用户在数字人组件上可以看到或操作：

1. 数字人形象
2. 当前字幕
3. 服务连接状态
4. 展开/收起按钮
5. 对话按钮
6. 声音开关按钮
7. “打招呼”快捷按钮
8. “讲解本页”快捷按钮
9. 文本输入框和发送按钮

#### 11.9.2 用户点击每个按钮后会发生什么

| 数字人入口 | 用户动作 | 前端行为 | 代理/API 链路 | 用户看到的结果 |
|---|---|---|---|---|
| 数字人本体 | 点击头像 | 服务在线时展开交互面板；离线时重新探测健康状态 | `checkHealth()` -> `/api/avatar/health` -> `avatar_service /health` | 连接成功后进入会话初始化或展开交互 |
| 对话按钮 | 打开/关闭对话面板 | 切换 chat 面板显示状态 | 本地 UI 状态 | 出现快捷按钮和输入框 |
| 声音按钮 | 开启/关闭数字人声音 | 切换 `avatarVoiceEnabled` | `useUserProfileStore` + `AvatarRenderer` 音频控制 | 有声音时自动播报；关闭时只显示字幕 |
| 打招呼 | 触发开场介绍 | 调用项目介绍播报 | `/api/avatar/project-intro` | 数字人做项目/课堂开场白 |
| 讲解本页 | 讲当前页 | 使用当前 slide_no 请求讲解 | `/api/avatar/ppt-explain` | 数字人讲解当前课件页 |
| 文本发送 | 发送用户消息 | 调用 broadcast 接口 | `/api/avatar/broadcast` | 数字人按当前会话上下文回应 |
| 服务未连接提示 | 点击重连 | 重新执行健康检查 | `/api/avatar/health` | 尝试恢复数字人连接 |

#### 11.9.3 数字人会话不是临时的，而是从课堂上下文构建的

数字人会话初始化时，前端会：

1. 读取当前课堂 `stage`
2. 提取有序 `scenes`
3. 从每一页动作里提取 `speech` 作为讲稿或摘要
4. 生成 `ppt_scripts`
5. 组装 `project_intro`
6. 把数字人形象地址、课堂主题等写入 `metadata`
7. 调用 `/api/avatar/session/load`

所以数字人不是脱离课堂单独说话，而是有课堂上下文、有页序、有摘要地参与课堂。

#### 11.9.4 数字人代理层怎么设计

前端不会直接裸连数字人服务，而是经过 Next.js API 代理：

1. `/api/avatar/health` -> `avatar_service /health`
2. `/api/avatar/session/load` -> 加载会话
3. `/api/avatar/project-intro` -> 生成开场白任务
4. `/api/avatar/ppt-explain` -> 生成本页讲解任务
5. `/api/avatar/broadcast` -> 普通播报/问答
6. `/api/avatar/media/...` -> 转发音频资源

这样做的价值是：

1. 前端统一只面对同域接口
2. 更容易接 runtime header
3. 更方便后续替换数字人后端

#### 11.9.5 数字人设置页也属于用户入口的一部分

数字人设置页里，用户可以直接配置：

1. 上传自定义头像
2. 选择“头像多模态解析模型”跟随全局模型或单独配置
3. 自定义多模态 `API Key / Base URL / Model ID`
4. 开关“启用数字人声音”

这意味着数字人的“形象”和“声音解析来源”都是前端显式可配置的，不是隐藏在代码里的硬编码参数。

#### 11.9.6 数字人声音为什么能更贴合形象

当前声音链路是：

1. 用户上传头像或使用默认头像
2. 头像地址和提示信息进入数字人会话元数据
3. 数字人后端的 `voice_profile` 服务调用多模态模型解析头像
4. 生成声音画像，如风格短句、声线建议、语速建议
5. 再把这些参数交给 TTS 提供者生成音频
6. 前端的 `AvatarRenderer` 读取 `audioUrl` 并自动播报

因此数字人的声音并不是“固定一个 voice 播到底”，而是有形象解析环节的。

### 11.10 导出、版本历史、课件打磨：交付层按钮详解

课堂页右上角还有一组与“最终交付”直接相关的按钮。

#### 11.10.1 打磨课件质量

“打磨课件质量”按钮不是导出按钮的一部分，而是一个独立的优化入口。它的作用是：

1. 基于当前后端 session 再次发送自然语言优化要求
2. 明确优化目标是 PPT、DOCX 或两者
3. 触发后端在已有结果基础上进行持续优化

这个按钮体现的是“二次打磨”能力，而不是初次生成。

#### 11.10.2 下载/导出菜单中每个按钮分别做什么

| 按钮 | 产物 | 执行位置 | 技术链路 |
|---|---|---|---|
| 导出 PPTX | 本地 PPT 文件 | 前端本地导出 | `useExportPPTX()` + `buildPptxBlob()` |
| 下载 DOCX 教案 | 后端 Word 文件 | 后端生成后下载 | `/api/artifacts/download?type=docx` -> backend artifact download |
| 导出教学资源包 | `PPTX + interactive HTML` 的 ZIP | 前端本地打包 | `JSZip` + `buildPptxBlob()` + 遍历 interactive scene HTML |
| 导出动画 GIF | 动画 GIF 文件 | 后端导出 | `/api/artifacts/export-gif` -> backend |
| 导出完整资源包 | 综合 ZIP 包 | 后端导出 | `/api/artifacts/bundle` -> backend |

#### 11.10.3 导出菜单不是一直可点的

前端会先判断导出条件：

1. 本地导出要求场景已全部生成完成
2. 失败 outline 必须已经处理完
3. 媒体任务必须全部完成或明确失败
4. 后端导出要求存在 `backendSessionId`

因此用户看到按钮可点/不可点，背后是完整的状态判断，不是简单禁用。

#### 11.10.4 版本历史 / 回滚

版本历史按钮会做两件事：

1. GET `/api/versions?sessionId=...` 拉取版本列表
2. POST `/api/versions` 携带 `session_id + version_id` 触发回滚

也就是说，版本历史不是静态展示，而是真正连到后端版本管理服务的。

### 11.11 课堂数据为什么能恢复：前端不是纯临时态

用户点击这些按钮后，很多状态不会因为刷新就消失，原因是课堂页做了多层恢复：

1. 场景数据先保存在本地存储。
2. 白板通过 Stage API 写回课堂状态。
3. 课堂页会把 `stage + scenes` 快照同步到 `/api/classroom`。
4. 媒体生成任务会从 IndexedDB 恢复。
5. 角色选择和部分设置由 Zustand 持久化。

这套设计保证了：

1. 白板不是写完即失
2. 数字人会话不是刷新即空
3. 课程生成不是离开页面就断层
4. 课堂是“可恢复运行时”，不是一次性渲染页

### 11.12 这一整套按钮系统的真正意义

这个项目的前端之所以有价值，不在于按钮多，而在于这些按钮不是孤立控件。它们共同构成了一套真实的课堂操作系统：

1. 首页按钮负责定义教学任务。
2. 课堂按钮负责执行讲课流程。
3. 白板按钮负责即时交互与痕迹保留。
4. 录音和发送按钮负责让用户实时进入课堂。
5. 数字人按钮负责讲解、播报和课堂拟人化。
6. 导出与版本按钮负责最终成果交付与可追溯修改。

因此，用户看到的是按钮，实际得到的是一套“可生成、可讲、可互动、可回滚、可交付”的前端教学工作台。

### 11.14 哪些按钮是纯前端，哪些按钮是真后端能力

从工程视角看，前端按钮可以分成三类：

#### 第一类：纯前端状态按钮

这些按钮不会直接打到后端：

1. 主题切换
2. 语言切换
3. 侧边栏折叠
4. 聊天区折叠
5. 输出类型勾选
6. 自动播放开关
7. 本地音量、静音、播放速度

它们的作用是控制体验，不直接产生命令式后端调用。

#### 第二类：前端写本地状态，但会被后续流程使用

这些按钮当下未必立即调后端，但它们写入的状态会在后续请求中真正生效：

1. 模型选择
2. PDF/参考资料上传
3. Web 搜索开关
4. 数字人多模态模型设置
5. 数字人头像上传

这类按钮更像“任务参数注入器”。

#### 第三类：点击就会命中真实后端服务

这些按钮和后端服务是一一对应的：

1. 首页“开始对话/发送” -> `/api/chat`
2. 首页“确认并生成课件” -> `/api/generate/scene-outlines-stream` + `/api/generate/scene-content`
3. 课堂录音 -> `/api/transcription`
4. 课堂状态恢复/同步 -> `/api/classroom`
5. 数字人相关按钮 -> `/api/avatar/*`
6. 版本历史/回滚 -> `/api/versions`
7. 后端工件下载 -> `/api/artifacts/*`

如果从“产品可落地性”角度看，真正体现系统不是纯前端 Demo 的，就是这第三类按钮。
